# KAI Sprint 2 repository execution

These instructions apply to the entire repository.

- Treat `KAI_Sprint2_P0_Final_Recovery_and_Implementation_Plan_v0.3.6.md` as the single living repository ExecPlan for KAI Sprint 2.
- Inspect the relevant implementation, tests, scripts, and documentation before every change.
- Read the ExecPlan's **Active execution contract** first. Current owner instructions and that section define the authorized outcome and package boundary. The historical ledger is evidence, not an executable backlog; its old package orders, preservation clauses and "stop here" checkpoints do not restart or override current work.
- Define packages around a complete user journey. Include every affected service, validator, persistence/read path, interface, test, generated asset and local policy document needed to make that journey consistent. Do not leave a demonstrated defect in that journey solely because it crosses an old package or layer boundary. Do not select unrelated product work.
- For authorized reporting work, missing reviews, unassessed support, ordinary uncertainty, coverage warnings and optional follow-ups are information, not approval prerequisites. Do not introduce a new queue, confirmation, reviewer, status or audience exception as a replacement barrier. Preserve attribution and accurate calculations; distinguish explicit processing/disclosure permission from evidence-quality review.
- Update the living ExecPlan evidence and status once, at the end of each coherent package.
- Before the first Node or npm command in every execution session, set `DATABASE_URL` to a non-listening loopback sentinel unless an explicit database target has been separately authorized. Keep the sentinel set for every later Node or npm command in that session.
- At each package boundary, run checks appropriate to the changed behavior and its risks, run `git diff --check`, inspect the complete diff, and create coherent local commits. Test the user's outcome, including generation and saved-report access; tests that merely preserve superseded approval barriers must be reconciled to the current owner-directed behavior.
- Continue through the authorized outcome without requesting continuation at routine implementation, test or local-commit milestones. A checkpoint applies only when it belongs to the current authorized work and explicitly requires an owner decision; a historical checkpoint is not a current checkpoint.
- Stop dependent work for an applicable unresolved authorization, required dependency decision, or technical failure that prevents the requested outcome. Name the exact operation, reason, applicable authority and smallest remedy, and continue independent authorized work. A legacy evidence-quality gate within an authorized removal package is a defect to repair, not a reason to preserve it or stop the package.
- Do not fetch, push, deploy, access or mutate databases or cloud services, inspect credentials or secrets, change feature flags, tenants, or production configuration, perform destructive actions, or update `00_KAI_CURRENT_STATE.md` without separate explicit authorization.
- Infrastructure Gates A through D and production mutations remain separately authorized unless current owner authorization explicitly establishes otherwise. They are distinct from the customer-facing evidence-quality approval barriers being removed. Honor authorization already granted in the conversation or active ExecPlan; do not ask for it again.
