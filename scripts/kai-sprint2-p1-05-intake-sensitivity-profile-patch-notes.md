# KAI P1-05 Patch Notes — Intake Sensitivity and Allowed-Use Profile Foundation

## Correction (classification-source and verification-integrity)

- Removed the invented `profile.sensitivity_committed_facts` / `personal_data` classification-producer contract. No currently authorized profiler, validator, review service, or producer emits a classification, consent, sensitivity, or permission fact; `kai.intake_file_profiles.profile` is machine-generated profiling metadata, never authoritative classification or consent input. The repository no longer selects `profile` from `kai.intake_file_profiles` at all - it loads only `organization_id`, `intake_file_id`, `file_profile_id`, `profile_canonical_sha256`. Every P1-05 classification status column and every pinned restriction now persists purely via the table's own `DEFAULT` values.
- `scripts/kai-sprint2-p1-05-intake-sensitivity-profile-runner-assertions.js` (added) - `assertNoFail`, copying the established P1-02 `assertNoFail` repository pattern. The runner (`-local-postgres.js`) now fails closed on a real `FAIL` status cell from the catalog verifier, read-only failure checks, or smoke verifier, while a check name merely containing `FAIL_CLOSED` never trips it. `__tests__/kai-sprint2-p1-05-intake-sensitivity-profile-runner-self-test.spec.js` (added) proves this deterministically.
- Fixed the catalog verifier's `CHECK_EXISTS` blocks: they previously used `WHERE EXISTS (...)` to filter the `unnest(...)` check-name array, so a missing constraint silently dropped its check row instead of reporting `FAIL`. The `PASS`/`FAIL` decision is now embedded in the `CASE` for every check, so every expected check always emits exactly one row. Added an `AUDIT_METADATA_BRANCH` check (previously missing) proving the metadata object-check constraint enforces the P1-05 branch.
- Making the runner honest surfaced a genuine pre-existing defect: three CHECK constraint names (`..._financial_records_status_check`, `..._indigenous_governance_status_check`, `..._story_testimonial_status_check`) exceeded PostgreSQL's 63-byte identifier limit and were silently truncated at creation, so the verifier's exact-name lookups never matched them. Shortened to `..._fin_records_status_check`, `..._indig_gov_status_check`, `..._story_testimonial_check` (all well under the limit) in the migration, verifier, and schema-contract spec.
- Replaced the smoke verifier's `transaction_and_audit_atomicity` probe: it previously forced a duplicate-key error on the already-seeded org1/profile1/dictionary1 identity, so the required audit insert was never reached. It now inserts a new, valid sensitivity profile and its required audit row against the still-unseeded profile2/dictionary2 lineage, confirms both inserts were reached, forces an exception, and proves both counts revert to their exact pre-block values.
- Added/updated boundary, schema-contract, and integration tests proving: profile JSON is never read for classification; `sensitivity_committed_facts` and `personal_data` and arbitrary classification-like JSON are all ignored; every classification status persists as `unknown` and every pinned restriction stays fail-closed regardless of profile content; the catalog verifier is total (every check name appears exactly once, and a missing constraint produces `FAIL` rather than a missing row).

## Behavior summary

One authoritative sensitivity/allowed-use profile row per `organization_id` + `file_profile_id` + `data_dictionary_id`. Same identity and stored profile hash: replay. Same identity, different bound profile hash: `conflict_current_state_changed`. Every applicable classification dimension - PII, minor data, health/housing/justice/immigration data, Indigenous/OCAP-like governance data (distinct from PII), staff notes, story/testimonial content, small-cell risk (distinct), consent basis, allowed use, and financial records (distinct from PII) - is its own CHECK-enforced 3-state column defaulting to `unknown`, which is a real, distinct, queryable value, never coerced to false/absent/safe/permitted. LLM processing, product learning, public use, and funder use are each pinned `not allowed`; human review is pinned `required`; retention posture is a single pinned labeled restriction, never an execution. Persisting the row and the required metadata-only `intake_sensitivity_profile_persisted` audit write happen inside one transaction; any audit rejection or publish failure rolls back the write. Dormant, tenant-scoped, and behind `KAI_SPRINT2_ENABLED` throughout.
